## Overview

I worked with a developer to redesign the internal admin platform of a mental health clinic. Using two recorded calls between the developer and the clinic’s product owners, plus the product requirement documents (PRDs), I audited existing workflows, mapped friction points across staff and patient journeys, restructured the information architecture and delivered high-fidelity prototypes with developer-ready handoff specs.

The research was secondhand, so the real work was synthesis: **turning recorded complaints into structured design problems** that a developer could build solutions for.

My goals going in:

* Reduce the time and cognitive load needed to retrieve patient documents and records.
* Consolidate high-frequency admin workflows: patient logging, appointment scheduling and document management.
* Modernise the interface to lower error rates and shorten onboarding for new staff.

## Problem Statement

The platform combined a lot of complexity with very little structure. Across the two call recordings and developer notes, four failure patterns kept recurring:

* **Rigid search.** Document retrieval required exact, case-sensitive keyword matches, and filters couldn’t be combined. Staff who didn’t remember a precise file name got stuck.
* **Redundant workflows.** Core tasks (logging a patient, booking an appointment, retrieving a document) involved unnecessary steps and unintuitive screen hierarchies.
* **Inconsistent patterns.** UI patterns changed from module to module, so new staff couldn’t build a reliable mental model, which stretched onboarding.
* **Weak hierarchy.** Poor information hierarchy led to missed and duplicated actions, especially in scheduling.

## Framing the Challenge

I went through the recordings and PRDs looking past surface complaints to the workflow problems behind them. The frustrations fell into three clusters: slow, unreliable document retrieval; scheduling errors caused by poor conflict visibility; and inconsistent labelling that made the interface hard to learn.

From this, I defined a primary persona:

* Admin staff (power users): high task frequency, constant switching between modules, and a need for fast retrieval with minimal navigation overhead. For them, **every extra click is a cognitive tax** in an already high-load environment.

## Design Ideation

Before moving to UI, I explored solutions for the two biggest failure points.

1. Document retrieval: keyword-only search was the biggest pain point for admin staff. I explored two directions: a natural language search bar (staff could type “Find Ngozi’s consent form from July”) and a structured multi-filter system (file type, date range, visibility, patient name). \
   I designed and prototyped natural language search first because it was the more ambitious option. When I reviewed it with the developer, it failed on two fronts: it needed complex backend logic, and staff trust in its results would be fragile. For an internal tool, it was **a low-trust, over-engineered solution**, so I replaced it with multi-filter search: faster to build, predictable, and matched to how staff already think about files. \
   I then added fuzzy matching, so a partial file name still returns relevant results, and removed case sensitivity, which made search far more forgiving.
2. Navigation architecture: I first designed a collapsible sidebar to free up space in a data-heavy interface. The developer’s input changed that: **staff use the sidebar as a spatial anchor** when moving between sections, so collapsing it forced them to re-expand and reorient on every switch. I kept it permanently visible and redesigned it with clearer icons, grouped sections and a stronger hierarchy. \
   I also considered breadcrumbs as a middle ground, but edge cases in the deeper document flows made them unreliable as an anchor.

## Usability Testing & Refinement

The developer and I tested the redesign against the specific workflow bottlenecks the CEO had flagged. Three refinements came out of those walkthroughs:

* Search results grouped by category: the first layout sorted results by recency, but staff look for a document type (a consent form, a therapy note), so **category grouping became the primary axis, not time**.
* Keyboard shortcuts for the highest-frequency admin actions: in a tool used 6–8 hours a day, removing hand-to-mouse switches compounds into real time savings.
* A shorter path to patient files: reaching a specific document took 4 clicks from the dashboard. Surfacing the document library on the patient profile card **cut it to 2**.

## Results

The redesign was validated through developer walkthroughs against the CEO’s documented pain points. The core retrieval and scheduling problems were solved at the structural level, and the developer confirmed the handoff specs were implementation-ready.

Outcomes of the redesign:

* Document retrieval moved from exact-keyword matching to a multi-filter system that works without prior knowledge of file names.
* **Patient file access went from 4 clicks to 2** from the dashboard.
* Overlap alerts surface scheduling conflicts before they happen, **eliminating silent double-bookings**.
* Consistent navigation patterns and a predictable module structure reduce onboarding friction for new staff.

The project wasn’t deployed. What it shows is how I work: extracting structured design problems from qualitative research, making and defending trade-offs under real constraints, and delivering designs, prototypes and specs a developer can build from.
